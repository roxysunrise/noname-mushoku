**负责人：角色模块设计与修改负责人**  
**适用范围：** `game/resources/app/src/character`、`game/resources/app/src/noname/init` 及其构建同步文件。

## 1. 负责人职责

负责人对角色技能从需求到交付的完整链路负责：

- 将用户意图整理成可执行的角色、技能和数值规则。
- 确认普通武将、Boss、联机模式和运行目录之间的适用范围。
- 只修改本次需求涉及的源码、翻译、注册和必要测试。
- 在交付前完成测试、构建和差异检查，并如实标注尚未验证的项目。
- 保留可回滚的变更边界，避免覆盖其他角色或既有功能。

## 2. 变更分级

| 等级 | 示例 | 最低控制要求 |
|---|---|---|
| S1 文案 | 技能名、描述、称号调整 | 源码与运行文件同步，检查引用一致 |
| S2 规则 | 触发时机、数值、目标、次数、响应方式 | 增加或更新针对性测试，运行相关测试 |
| S3 结构 | 新角色、Boss注册、联机席位、跨模块联动 | 完整相关回归、构建、必要的引擎烟测 |
| S4 发行 | 安装包、APK、GitHub Release | 在S3基础上进行对应平台验证并单独记录产物 |

用户未明确要求时，S1至S3只同步本地运行目录，不自动生成发行包。

## 3. 标准流程

### 3.0 头像资产

新增角色默认通过 imagegen 技能官方脚本调用 API，使用 `gpt-image-2`，Python 通过 `conda run -n imagegen` 执行（用户于2026-10-21再次确认，后续无需重复询问调用方式）。为每名角色保留生成原图、提示词和游戏实际使用文件，并将最终头像复制到运行目录后验证可加载。凭据仅从环境读取；生成失败时如实记录，不得用 SVG 剪影冒充成品。

### 3.1 需求确认

先记录角色版本、技能名称、触发时机、数值、目标、次数限制、响应方式、例外和适用模式。存在歧义时，采用最小改动并在交付中列出假设；不得擅自改变其他数值。

### 3.2 设计审查

设计必须说明：

- 技能解决的玩法问题和角色主题；
- 与牌、装备、花色、资源及其他技能的关系；
- 是否会循环触发、叠加失控或绕过引擎正常结算；
- 普通版与Boss版是否独立，是否影响联机和AI。

联动优先通过触发条件和游戏行为实现，不通过指定角色姓名或角色ID硬编码。数量词按字面实现，明确“至少”“大于”“首次”“每回合”等边界。

### 3.3 实现控制

源码优先修改 `src` 目录；翻译同步修改对应 `*-translate.js` 或注册文件。动态牌转换、目标、距离、无懈和响应交给引擎原生流程处理。不得把占位头像、测试夹具或调试代码当作正式交付内容。

### 3.4 验证控制

至少执行：

1. 本次规则对应的单元测试或回归测试；
2. `npm`/构建脚本涉及的构建命令；
3. `git diff --check` 和源码、运行文件差异检查。

S3或涉及引擎结算的改动，增加隔离引擎烟测。测试通过只证明所覆盖的实现路径，不代表多人平衡、手机真机或长期运行已经验证。

### 3.5 交付记录

交付说明必须写明：修改文件、规则变化、测试命令与结果、构建结果、实际同步目录、未验证边界和生效方式。运行中的页面不会热更新；需要重载或重启，已开始的对局通常需要重新开局。

## 4. 回滚与冲突处理

- 修改前重新读取目标文件并检查工作区差异。
- 发现并发修改时，保留对方变更，停止覆盖式写入，按最小补丁合并。
- 回滚只撤销本次变更涉及的文件和行，不使用强制重置或覆盖无关工作。
- 发行失败、测试失败或同步失败时，报告失败点和未完成项，不宣称已交付。

## 5. 上传边界

大更新完成并通过相关验证后，按项目约定检查远端、提交并推送到 `origin`；小改动可积累。提交中不得包含凭据、缓存、依赖目录或临时文件。只有推送成功后才能称为“已上传”，并提供分支和提交标识。
